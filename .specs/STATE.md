# STATE

## Decisions

### AD-001
- **Decision**: Backend em Go (chi + pgx/v5 + jwt/v5 + zap + cobra), TLS automático via CertMagic embutido (sem proxy externo), frontend React embutido no binário via `go:embed`.
- **Reason**: Resolve o risco técnico mais crítico do produto (TLS automático por domínio dinâmico cadastrado em runtime) com biblioteca madura da própria equipe do Caddy, entregando binário único de baixo footprint — essencial pra adoção de uma ferramenta self-hosted open source. Stack alinhada à já validada em produção em `baas/zeep-orbit`.
- **Trade-off**: Time trabalha mais com Node/React no dia a dia; Go nesse serviço específico tem menos familiaridade acumulada que Node.
- **Scope**: Todo o backend do projeto (zeep-vane) — API, poller, roteamento por domínio, TLS.
- **Date**: 2026-08-06
- **Status**: active

### AD-002
- **Decision**: Cada instalação self-hosted atende exatamente 1 empresa. Não existe tabela/coluna de tenant (`company_id`) em nenhum schema.
- **Reason**: Isolamento total de dado por deploy é mais simples e mais seguro que multi-tenancy real; bate com o modelo de distribuição (empresa roda a própria infra).
- **Trade-off**: Se o modelo de negócio mudar pra SaaS hospedado multi-cliente no futuro, exige retrofit de tenant em todas as tabelas.
- **Scope**: Todo o schema de dados do projeto.
- **Date**: 2026-08-06
- **Status**: active

### AD-003
- **Decision**: Múltiplos admins com papéis fixos (`owner`, `operator`, `viewer` — sem matriz de permissão configurável) reentram no MVP, via feature própria `admin-dashboard`. Remove RBAC do Out of Scope do `mvp-core` (mantém SSO/SAML fora).
- **Reason**: Sem UI/dashboard, os 25 requisitos admin do `mvp-core` (SP-01 a SP-25) só são operáveis via chamada direta de API. Usuário decidiu que múltiplos admins com papéis diferentes é necessário já na v1, não pós-MVP.
- **Trade-off**: Aumenta escopo do MVP (nova tabela de roles/permissions, checagem de autorização por endpoint, UI de gestão de admins) além do que AD-002 (single-tenant, sem multi-tenant) previa como simplificação.
- **Scope**: Autenticação/autorização do dashboard administrativo e endpoints do `mvp-core` que passam a exigir checagem de papel.
- **Date**: 2026-08-06
- **Status**: active

### AD-004
- **Decision**: Token de sessão do admin no frontend vive em cookie `httpOnly`/`Secure`/`SameSite=Strict` setado pelo backend no login — nunca em `localStorage`/`sessionStorage`, nunca lido ou decodificado por JavaScript no client.
- **Reason**: Decisão explícita do usuário durante o Design de `admin-frontend`. Cookie `httpOnly` elimina por completo a superfície de XSS-rouba-token (JS não tem acesso de leitura), diferente de qualquer storage acessível via script. `SameSite=Strict` mitiga CSRF numa API JSON same-origin. O papel do admin continua vindo sempre de `GET /api/auth/me` (AF-34) — o JWT não carrega claim de role (só `sub`/`iat`).
- **Trade-off**: Exige mudança aditiva no backend (login passa a também setar cookie além do corpo `{token}` já existente; `RequireAuth` passa a aceitar cookie além do header `Authorization`; novo endpoint `POST /api/auth/logout` para limpar o cookie). Mudança é 100% aditiva — nenhum teste/consumidor existente do login ou do middleware quebra. `Secure` exige HTTPS mesmo em desenvolvimento local.
- **Scope**: Qualquer feature de frontend deste projeto que lide com o token de sessão do admin.
- **Date**: 2026-08-19
- **Status**: active (revisada no mesmo dia, antes de Tasks/Execute — versão anterior desta entrada, que propunha `sessionStorage`, nunca chegou a ser implementada)

### AD-007
- **Decision**: Integração backend real do `admin-frontend` (pós-AD-006) dividida em 6 etapas sequenciais e testáveis isoladamente (Etapa 0 Fundação → 1 Domínios/Status Pages/pública → 2 Integrações/Serviços → 3 Incidentes → 4 Admins → 5 Poller), substituindo T1-T8 e o wiring pendente de T13/T14/T18/T21/T24/T28/T31/T33 em `tasks.md` por tasks novas I1-I20. 3 sub-decisões tomadas com o usuário durante o planejamento:

A investigação também achou 2 gaps que o `tasks.md` original nunca cobriu (resend/cancel de convite, company settings); usuário decidiu não expandir escopo agora.

Endpoint dev/preview de status page pública (item 2) é superfície extra a manter que não existe em produção — decisão consciente de simplicidade de dev sobre fidelidade total à arquitetura de produção. `AdminsPage`/`SettingsPage` ficam com funcionalidade parcialmente indisponível até rodada futura.
- **Scope**: Integração backend real de `admin-frontend` (`web/` + endpoints Go correspondentes) desta rodada. Backlog (resend/cancel invite, company settings) fica para rodada futura.

### AD-008
- **Decision**: O endpoint de preview autenticado (`GET /api/status-pages/{id}/public-preview`) deixa de exigir `state == "published"` — passa a compor a resposta pra uma status page em qualquer estado, incluindo sem domínio nenhum anexado (`domain_id: null`).
- **Reason**: Feature `status-page-domain-attach` (2026-08-23) — teste manual do usuário revelou que hoje é impossível visualizar uma status page recém-criada antes do domínio ter DNS resolvido e certificado TLS emitido, porque o preview foi desenhado deliberadamente em `AD-007`/I12 pra espelhar o gate de produção 1:1 ("pra o preview e a página de produção nunca discordarem do que conta como visível"). Esse objetivo original é exatamente a causa do bug: um admin que quer pré-visualizar antes de ir ao ar não tem caminho nenhum se o preview insiste em bater um estado de produção que ainda não existe.
- **Trade-off**: Preview e produção agora podem "discordar" (preview mostra conteúdo de página `draft`/sem domínio que a produção real nunca serviria) — aceito porque o preview já é autenticado/admin-only e nunca foi o caminho público real; fidelidade total a produção não tem valor pra esse caso de uso.
- **Scope**: `internal/api/public_status_preview_handler.go` — não afeta `PublicStatusHandler.Get`/`router.HostRouter` (caminho público real de produção, que continua exigindo `published`).
- **Date**: 2026-08-23
- **Status**: active (supersede parcial do item 2 de `AD-007` — a decisão de ter o endpoint dev/preview continua válida, só a regra de "espelhar produção 1:1" foi revertida)

### AD-009
- **Decision**: Features que tocam deployment (Dockerfile, docker-compose, Makefile build targets, convenções de bootstrap/embed) devem por padrão espelhar as convenções já provadas em produção de `baas/zeep-orbit`, a menos que haja uma razão específica do Vane pra divergir.
- **Reason**: `self-hosted-docker-bootstrap` (2026-08-24) fechou a promessa de `AD-001` ("frontend embedded via `go:embed`") que nunca tinha sido implementada de fato (confirmado por `grep -r "go:embed"` retornando vazio antes desta feature), e o fez espelhando deliberadamente o Dockerfile/docker-compose/Makefile/bootstrap já funcionando de `zeep-orbit` em vez de desenhar um padrão novo — decisão explícita do usuário durante o Design ("preciso que o comando de subida seja igual o que existe hoje no orbit que ja funciona"). O resultado (single-stage `FROM scratch`, `LOCK TABLE ... IN EXCLUSIVE MODE` pro bootstrap race, `go:embed` no mesmo diretório do asset por causa da restrição de `..`) validou que reusar um padrão já testado em produção evita reinventar decisões que `zeep-orbit` já errou e corrigiu uma vez.
- **Trade-off**: Onde Vane tem restrição que Orbit não tem (migrations reais via `golang-migrate`, listener TLS público de status page), o espelhamento não é 1:1 — exige julgamento caso a caso sobre o que é "a mesma convenção adaptada" vs. "um padrão realmente novo". Seguir esse default cegamente sem checar se a diferença é real pode importar uma decisão errada do Orbit pro Vane.
- **Scope**: Qualquer feature futura deste projeto que toque Dockerfile, docker-compose.yml, Makefile de build, ou fluxo de bootstrap/deploy inicial.
- **Date**: 2026-08-24
- **Status**: active

### AD-011
- **Decision**: `pgxpool.MaxConns` limitado a 4 por pool (`internal/db/pool.go`), inclusive no pool único de produção.
- **Reason**: Causa raiz confirmada do flake `L-017` — sem cap, cada pool assumia o default `max(4, NumCPU())`; com ~17 pacotes de teste de integração abrindo pool próprio sob paralelismo do `go test`, o total de conexões concorrentes podia estourar o `max_connections` do Postgres. Provado deliberadamente (reprodução da mesma falha noutro teste ao reduzir `max_connections` do servidor).
- **Trade-off**: 4 é suficiente pra escala atual do MVP (1 instalação = 1 empresa, AD-002); reavaliar se volume de tráfego por instalação crescer.
- **Scope**: `internal/db/pool.go`, todo consumidor de pool (produção + testes de integração).
- **Date**: 2026-08-28
- **Status**: active — commit confirmado

### AD-012
- **Decision**: Qualquer endpoint de lista futuro que precise paginar segue o padrão de `list-pagination` (2026-08-28): offset-based (`page`/`page_size` via `LIMIT`/`OFFSET`, não cursor), envelope `{items,total,page,page_size}` (`internal/api.Page[T]`), `page_size` fixo por endpoint (sem `?page_size=` configurável), `total` via `COUNT(*) OVER()` com fallback `SELECT COUNT(*)` só quando a página vem vazia, `?page=` inválido/ausente vira `1` sem erro 400. Repositório com caller interno não-HTTP (ex. poller) ganha `ListPaginated` novo em vez de mutar `List(ctx)` existente.
- **Reason**: `list-pagination` fechou 9 endpoints sem paginação nenhuma (nem `LIMIT`). Só `incidents` (admin) cresce sem limite de verdade hoje; os demais são pequenos por design (AD-002), mas o usuário decidiu aplicar o padrão em todos os 9 pra consistência, excluindo só `admin_audit_log` (sem rota de leitura) e `status_intervals` (já bounded por janela de tempo, contrato usado por `internal/history`).
- **Trade-off**: Esforço mecânico em endpoints que não precisam (dezenas de linhas) — aceito pelo usuário em troca de consistência de padrão em todo o painel admin.
- **Scope**: Qualquer `Repository.List`/handler futuro que hoje devolve array cru sem `LIMIT`.
- **Date**: 2026-08-28
- **Status**: active

### AD-013
- **Decision**: Cross-replica coordination (poller leader election, per-IP rate limiting, CertMagic certificate storage) is implemented via Postgres — session-scoped `pg_advisory_lock` on dedicated connections for mutual exclusion (`internal/pglock`, new), plain shared tables for state that doesn't need exclusion (`rate_limit_buckets`, `certmagic_storage`) — never via new infrastructure (Redis, etcd, NFS, object storage).
- **Reason**: `ha-multi-replica` (2026-08-30) closed the three concrete gaps blocking `charts/zeep-vane/values.yaml`'s `replicaCount` default above 1: the poller had no leader election, `internal/ratelimit.IPLimiter` was an in-memory map by its own doc comment, and `certmagic.FileStorage` wrote to local disk requiring a `ReadWriteOnce` PVC that can't be shared across pods. Postgres is already the project's sole mandatory dependency (extends the reasoning already behind `AD-010` logo storage and `AD-011` pool sizing) — coordinating through it avoids introducing a second stateful dependency an operator would have to run and back up.
- **Trade-off**: Every rate-limit check and CertMagic storage operation now does a Postgres round-trip instead of an in-memory/local-disk one; accepted because both are low-volume by nature (a handful of credential-sensitive routes; infrequent cert issuance/renewal for a self-hosted install). Session-advisory-lock holders keep one dedicated connection open outside `db.Pool`'s `MaxConns=4` cap for as long as they hold the lock — bounded (at most one per replica attempting poller leadership, plus one per concurrently-issuing hostname), not unbounded.
- **Scope**: Any future feature needing cross-replica coordination or shared state in this project should default to a Postgres-backed mechanism (advisory lock or shared table) before considering new infrastructure.
- **Date**: 2026-08-30
- **Status**: active

### AD-013 addendum: Restart gated behind leadership, bounded heartbeat probes

- **Decision**: `PollerManager.Restart` now checks a new `leading atomic.Bool` field (set by `RunLeaderLoop` around its acquire/lose-leadership transitions) and no-ops if this replica isn't currently leading. `heartbeatUntilLost`'s `handle.Healthy()` probe is now wrapped in `context.WithTimeout(ctx, m.leaderHeartbeatInterval)` instead of the process-lifetime `ctx`.
- **Reason**: found by the same independent Opus pre-release review that produced the `AD-019 addendum` above, auditing everything shipped since `v0.2.2`. `Restart` never actually checked leadership - only `RunLeaderLoop` calling it did. `IntegrationsHandler.ConnectDatadog` (`internal/api/integrations_handler.go`) also calls `Restart` directly, and the admin API is served by every replica, not just the leader - a non-leader replica handling that request started a second, unmanaged poller alongside the real leader's, contradicting AD-013's own "at most one replica ever runs a poller at a time" premise (HA-01). Separately, an unbounded `SELECT 1` heartbeat could block past `leaderHeartbeatInterval` on a Postgres restart/partition, risking transient double leadership while a stuck heartbeat still believed it held the lock.
- **Trade-off**: a Datadog credential connected/rotated through a non-leader replica no longer takes effect on that replica - it takes effect once whichever replica is actually leading acquires or already holds leadership and (for a leadership change) calls its own `Restart` from the stored integration. In practice this is at most one leader-election cycle behind, not indefinitely delayed, since `RunLeaderLoop` always restarts from the currently stored integration on every acquisition. A leader that never loses leadership and was already running before the credential changed would not pick it up until it does lose and reacquire leadership (or the process restarts) - a known residual gap, not fully closed by this fix, flagged for a future cross-replica notification mechanism (e.g. Postgres `LISTEN`/`NOTIFY`) if it proves to matter in practice.
- **Scope**: `internal/cli/poller_manager.go` (`leading` field, `Restart`, `RunLeaderLoop`, `heartbeatUntilLost`), `internal/cli/poller_manager_test.go` (existing direct-`Restart` tests updated to set `leading` first; new `TestPollerManager_Restart_NotLeading_IsNoOp`).
- **Date**: 2026-09-08
- **Status**: active

### AD-014 addendum: VANE_ADMIN_BASE_URL requires a scheme

- **Decision**: `config.Load()` now rejects a non-empty `VANE_ADMIN_BASE_URL` that doesn't start with `http://` or `https://`.
- **Reason**: same Opus pre-release review - an operator typo (`admin.example.com` instead of `https://admin.example.com`) passed `Load()` silently; `adminBaseURL()` still built a link from it, which most mail clients linkify to a plain `http://` URL in a password-reset/admin-invite email. Not attacker-controlled (trusted config, AD-014's original threat model - host-header injection from an unauthenticated request - is unaffected and stays closed), but worth failing loudly at boot instead of producing a working-looking wrong link later.
- **Trade-off**: none of substance - a deploy with a malformed `VANE_ADMIN_BASE_URL` now fails to boot instead of booting with broken email links; this is the same posture `requireSecret`'s placeholder-secret rejection already takes for a different config mistake.
- **Scope**: `internal/config/config.go` (`Load`), `internal/config/config_test.go`, `.env.example`/`docker-compose.yml` (previously didn't document this variable at all).
- **Date**: 2026-09-08
- **Status**: active

### AD-014
- **Decision**: `PasswordResetHandler.Request` now actually sends the reset email via `email.Service.SendPasswordReset` (mirrors `AdminsHandler.sendAdminInviteEmail`/`SendAdminInvite` exactly), superseding the AD-012-era-adjacent note in the `admin-invite-resend-cancel` handoff below ("Envio de email loga o token ao invés de enviar de verdade") — that was already true only for password-reset, not admin-invite, and is now true for neither. Two follow-on decisions ship with it: (1) every admin-facing email link (password-reset AND admin-invite, both changed together) is built from a new required-for-production config value, `VANE_ADMIN_BASE_URL` (`Config.AdminBaseURL`, `internal/api.adminBaseURL()`), never from the incoming request's `Host` header; when unset, links fall back to a visibly-broken placeholder host rather than trusting `Host`. (2) `Request`'s email send is dispatched in a detached goroutine (`context.WithoutCancel(r.Context())`) instead of awaited, so the endpoint's response time doesn't depend on whether the outbound provider call happens at all.
- **Reason**: An independent Opus review of the diff introducing this feature (before it was committed) flagged that building the emailed link from `r.Host` on an *unauthenticated* endpoint (unlike admin-invite, which requires an authenticated owner/operator) is a host-header-injection primitive for account takeover — an attacker names an arbitrary `Host` and a victim's email address, and the victim receives a legitimate-looking email whose link points at the attacker's chosen host. The same review found that awaiting the send synchronously reintroduced a timing-based account-enumeration oracle (a known email now takes an outbound HTTPS round-trip longer to respond than an unknown one), undermining the identical-response-shape protection `Request` is built around.
- **Trade-off**: `VANE_ADMIN_BASE_URL` is a new operator-facing config value with no safe zero-config default (unlike `VANE_HTTPS_ENABLED`/`VANE_SECURE_COOKIES`, which default to the safer choice) — an operator who hasn't set it gets non-functional email links rather than a silently-insecure but "working" deploy. Considered and rejected: falling back to `r.Host` when unset (reintroduces the vulnerability for anyone who doesn't set it, i.e. almost every deploy on day one) and requiring it at `config.Load()` time like `DATABASE_URL` (would fail every existing deploy's boot until the operator adds one more env var, for a link that's cosmetically broken rather than fatal until they connect an email provider).
- **Scope**: Any future admin-facing email link (or any link embedded in outbound communication to an admin) must build its base URL from `cfg.AdminBaseURL` via `internal/api.adminBaseURL()`, never from `r.Host` or another per-request value. Any future unauthenticated endpoint that triggers an external side effect keyed off attacker-suppliable state (email send, webhook, etc.) should default to dispatching it detached rather than awaiting it inline, when the awaited latency would vary based on which branch of an enumeration-sensitive check was taken.
- **Date**: 2026-08-31
- **Status**: active

### AD-015
- **Decision**: An admin's `name` (required) and `phone` (optional) are collected once, at invite/bootstrap time — never re-collected from the invitee at accept time. `admins`/`admin_invites` both gained `name TEXT NOT NULL DEFAULT ''`/`phone TEXT` columns (migration `0019_admin_name_phone`); `AcceptInvite` copies `invite.Name`/`invite.Phone` onto the new `Admin` row unchanged. `phone` has a loose server-side format check (`internal/api.ValidatePhone`: optional, digits + `+ ( ) -` only, ≤32 chars) since Vane never dials the number itself — it exists so an admin who bypasses the frontend can't post arbitrary length/character garbage into the column, not to validate a real phone number.
- **Reason**: The inviter (an existing owner/operator) already knows the invitee's name for real-world identification purposes (support tickets, audit log readability, "who is admin X"); asking the invitee to type it again at accept time is a redundant step in a flow whose only other input is a password. Same reasoning `AcceptInvite` already applies to `role` (also set by the inviter, not the invitee).
- **Trade-off**: A typo in the name/phone the inviter enters can only be corrected by an owner re-inviting or a future "edit admin" endpoint (doesn't exist yet) — there is no self-service profile edit for the invitee. Accepted since this mirrors how `role` already works and the fields are informational, not security-relevant.
- **Scope**: Any future required-at-signup field for an invited admin should default to being collected from the inviter, not the invitee, unless the field is inherently something only the invitee can supply (e.g. the password itself).
- **Date**: 2026-08-31
- **Status**: active

### AD-016
- **Decision**: `PhoneField` (`web/src/components/ui/PhoneField.tsx`) uses `@zeeptech/toolkit` (a ZeepLabs-authored npm package, not an Anthropic/Starbem one) for its country list and phone mask, imported from the package's deep subpaths — `@zeeptech/toolkit/dist/masks` and `@zeeptech/toolkit/dist/utils/countries` — never from the root `@zeeptech/toolkit` barrel.
- **Reason**: The root barrel is CommonJS (`require`/`__exportStar` re-exports, `dist/index.js`), which Rollup/Vite cannot tree-shake even though the package declares `sideEffects: false` — importing just `{ countries, globalCellphoneMask }` from the barrel pulled in every other module transitively, including `utils/brazilian-cities.js` (~180KB uncompressed, completely unrelated to phone masking) and the full `dates`/`validators`/`normalize`/`diacritics` modules. This inflated the production bundle from 127KB to 186KB gzip (+46%) for two functions. Deep-importing only the subtree that `globalCellphoneMask` actually needs (`masks`, which itself requires `utils/countries`) dropped the regression to 141KB gzip (+11%) with identical runtime behavior.
- **Trade-off**: The deep-import paths (`@zeeptech/toolkit/dist/...`) reach past the package's declared `main`/`types` entrypoints into its build output directly, since the package has no `exports` map restricting subpaths and ships no per-module entrypoints at its root. This is coupled to the package's current internal directory layout (`dist/masks/`, `dist/utils/countries`) — a future `@zeeptech/toolkit` release that reorganizes `dist/` or adds an `exports` map blocking deep imports would break this at build time (loud, not silent) and require re-verifying the import paths.
- **Scope**: Any future dependency added for a narrow feature (a single mask, a single formatter) should be checked for tree-shakeability before adopting — prefer a package with real ESM + an `exports` map, or a deep/subpath import like this one, over trusting `sideEffects: false` alone on a CJS package.
- **Date**: 2026-08-31
- **Status**: active

### AD-017

### AD-019 addendum: fixed-width lagged window replaces window = p.interval

- **Decision**: `pollService`'s window is no longer `to := time.Now(); from := to.Add(-p.interval)`. Two new package constants in `internal/poller/poller.go` decouple the fetch window from the poll cadence: `recentWindowWidth = 5 * time.Minute` (how much history is requested) and `recentWindowLag = 60 * time.Second` (how far the window's end is offset behind `time.Now()`). New computation: `to := time.Now().Add(-recentWindowLag); from := to.Add(-recentWindowWidth)`. `POLL_INTERVAL_SECONDS`'s example default changed `60` → `120` (`.env.example`, `docker-compose.yml`, `charts/zeep-vane/values.yaml`, README) to match the public status page's own 2-minute refresh cadence — it now controls poll frequency only, not window shape.
- **Reason**: an independent Opus pre-release review (dispatched to validate everything since `v0.2.2` before cutting a new release) live-tested the original `window = p.interval` design against the same real SLO (`conversations-service`) that motivated AD-019, and found it reproduces the exact bug it was meant to fix. At ~51 req/min steady traffic, the freshest 60s reported as few as 8 requests (Datadog's trace-metric aggregation lags 1-2 minutes behind real time), which either (a) tripped `minRecentWindowRequests` and carried a stale status forward - the original stuck-on-"interrupção" symptom - or (b) computed the SLI on a genuinely incomplete window, producing a false breach. Confirmed live: 120-180s-old data already matched the steady rate. Discussed interactively with Julio (2026-09-08) before implementing; user chose a fixed 5-minute width with a 60s lag over widening `p.interval` itself, to keep poll cadence aligned with the public page's 2-minute refresh while giving the SLI computation a stable, already-aggregated sample.
- **Trade-off**: a wider window (5m vs the original ~1m) means a real recovery takes up to ~5-6 minutes to surface on the public page instead of ~1-2 - accepted as still far better than the 30-day staleness AD-019 replaced. The 60s/5m constants are, like `minRecentWindowRequests`, live-measured against one SLO's traffic pattern, not derived from a broader sample - same "unconfirmed floor, easy to tune later" caveat applies.
- **Scope**: `internal/poller/poller.go` (`recentWindowWidth`, `recentWindowLag`, `pollService`), `internal/poller/poller_recent_window_test.go` (window-bounds test rewritten to assert against the new constants instead of `p.interval`), `.env.example`, `docker-compose.yml`, `charts/zeep-vane/values.yaml`, `README.md` (config table + dev-setup example), `CHANGELOG.md` `[Unreleased]`. No new tests added beyond the rewritten one - the low-volume/carry-forward/first-poll tests were already width/lag-agnostic (they assert on `RequestCount`, not window bounds).

### AD-019 addendum 3: breach hysteresis - 2 consecutive cycles required before flipping to outage

- **Decision**: `pollService` no longer flips a service to `"outage"` on a single Datadog `state: "breached"` response. A new package constant `breachHysteresisCycles = 2` and a per-service counter (`Poller.breachStreak map[string]int`) require 2 consecutive polling cycles reporting `"breached"` before `current_status` actually becomes `"outage"`; a single breached cycle carries the previous status forward instead (same carry-forward mechanism `minRecentWindowRequests` already used), and any non-breached result resets the streak to 0.
- **Reason**: found by a **third** independent pre-release Verifier pass (dispatched after the second round of fixes above), and confirmed live against a real, 30-day-healthy SLO (`api-gateway`, 99.95%/90.9% budget remaining). Root cause: Datadog computes `overall.state` for *any* requested window against the SLO's configured `target` (typically 99.5% over 30 days) **without rescaling that target to the window's width**. Applying a 30-day-calibrated 99.5% threshold to a 5-minute bucket is drastically stricter - a single request failing out of a couple hundred is enough to trip `"breached"`. Live measurement: 6 consecutive 5-minute windows against `api-gateway`, each with 8k-13k requests (well above `minRecentWindowRequests`, so the existing low-volume guard does not help here), and **2 of the 6 came back `"breached"`** despite the SLO being healthy over 30 days. Without hysteresis, this flaps the public page between "operational" and "outage" multiple times an hour on high-traffic services - and `internal/history/hourly.go`'s worst-status-wins hourly bucketing then paints the *entire hour* red in the public uptime history from a single bad window, which is worse than the staleness bug AD-019 was originally written to fix.
- **Trade-off**: this is an explicitly named **stopgap**, not the definitive fix. It absorbs single-window noise (2 consecutive breaches is a much rarer event than 1) but does not correct the root statistical mismatch - a real, sustained outage large enough to breach 2 consecutive 5-minute windows still surfaces correctly, but a genuinely short (single 5-minute-window) real outage on a high-traffic service is now, by design, treated the same as noise and carried forward instead of shown. 2 cycles was chosen as the smallest number that already resolved the observed 2-breached-out-of-6 noise rate in the live sample; it has **not** been calibrated against a broader sample of services/time (same "unconfirmed floor, easy to tune" caveat as `minRecentWindowRequests`, `recentWindowWidth`, `recentWindowLag`). Detection latency for a real outage is now up to `2 * POLL_INTERVAL_SECONDS` (up to ~4 minutes at the new 120s default) instead of one cycle. **Correction (fourth independent Verifier, F-5, see the Handoff section below for full detail)**: "2 consecutive polling cycles" is imprecise - a low-volume window (`RequestCount < minRecentWindowRequests`) between two breached windows neither resets nor advances the streak, so 2 breached windows that aren't literally adjacent in time can still sum to a flip. And `Poller.breachStreak` is in-memory per `*Poller` instance, so a Datadog credential rotation or an HA leadership handover (both of which construct a fresh `Poller` via `PollerManager.Restart`) resets an in-progress streak, adding up to one more cycle of detection latency in that specific circumstance.
- **What a robust, definitive fix would need to look like (not implemented - flagged for a future session, do not silently build this)**:
  1. **Stop reusing `overall.state` as-is.** It is fundamentally the wrong signal for a sub-window query: it is Datadog's SLO-compliance verdict computed against a target calibrated for a completely different (usually much longer) window width. The fix belongs in *what's compared*, not in how many times it's compared.
  2. **Compare `overall.sli_value` against a threshold picked for the window width actually being queried**, not the SLO's configured 30-day `target`. This requires either (a) a separate, explicitly-configured "recent-window" threshold per service/SLO (more config surface, but statistically honest), or (b) a statistically-derived tolerance band around the window's own expected error rate (more complex, no external config needed, but needs enough historical samples to calibrate per-service - cold-start problem for a newly connected service).
  3. Whichever direction is chosen, **it needs its own real-traffic measurement pass** across more than one SLO and more than 6 samples before shipping - the same live-data discipline this whole AD-019 lineage has used at every step, not a guess. `api-gateway`'s 99.5%/30d target and its real traffic pattern is one data point; other self-hosted deployments will have different SLO configurations and traffic shapes, and the eventual constant/formula needs to hold up across a spread of them, not just this one account.
  4. Consider whether hysteresis (cycle count) and threshold-rescaling (statistical correctness) are complementary rather than exclusive - a correctly-rescaled threshold reduces false breaches at the source; hysteresis is still cheap insurance against genuine short blips once the threshold itself stops being systematically wrong.
  5. Any of this needs a fresh `tlc-spec-driven` Specify pass (EARS acceptance criteria, explicit assumptions section) before implementation - this is exactly the kind of "ambiguity, new domain, needs a decision only the user can make with real data" situation the skill's Complex-scope row is for, not a same-session "corrige tudo" fix.
- **Scope**: `internal/poller/poller.go` (`breachHysteresisCycles`, `Poller.breachStreak`, `pollService`), `internal/poller/poller_recent_window_test.go` (3 new tests: single breach carries forward, 2 consecutive flips to outage, an intermediate ok resets the streak), `internal/poller/retry_test.go` (`fakeProvider` gained an optional `statuses []datadog.SLOStatus` field to return a different status per call). Discrimination sensor run: reverting the hysteresis branch back to `current = normalizeStatus(status.State)` made 2 of the 3 new tests fail as expected (the third, 2-consecutive-breaches, correctly passes either way since it doesn't exercise the single-breach carry-forward path - not a gap, it just isn't the discriminating test for this mutation). Commit `c5c5c85`.
- **Date**: 2026-09-08
- **Status**: active - stopgap, not the definitive fix (see item 4 above)

### AD-021

- **Decision**: `llm-slo-analysis` adds a second `internal/llm` package that reuses three patterns already established by `internal/email`/AD-005-style precedent rather than inventing new ones: (1) a two-table schema (`llm_providers` for connected-provider rows keyed by provider name, `llm_settings` for the single active-provider pointer), mirroring `email_providers`/`email_settings` exactly (migration `0021_llm_providers`, commit `8b8a65b`); (2) an `llm.Provider` adapter interface (`Complete`, `ValidateCredentials`) plus `llm.ProviderFactory`, mirroring `internal/email/provider.go`'s shape field-for-field so a second provider (Anthropic, etc.) could be added later the same way `resend`/`sendgrid` were (commit `5136a04`); (3) a detached-goroutine-with-bounded-timeout pattern for every LLM enrichment call `SLOAnalyzer.HandleTransition` dispatches - `context.WithTimeout(context.WithoutCancel(ctx), analysisTimeout)`, `analysisTimeout = 30 * time.Second` (`internal/poller/analyzer.go`), logging and discarding the result on any error/timeout rather than blocking the poll cycle or a public-page request on OpenAI's latency (commit `f31124f`). No new environment variable exists for `analysisTimeout` - it stays a hardcoded constant, matching `internal/poller/poller.go`'s existing tuned-constant convention (`POLL_INTERVAL_SECONDS` is a real knob; the enrichment timeout deliberately isn't, since a slower-than-usual completion costs nothing but delaying one incident's enrichment, per the constant's own doc comment).
- **Reason**: reusing `email`'s schema/adapter shape rather than inventing an LLM-specific one keeps the codebase's "one way to connect a third-party credentialed service" story intact - an operator who already understands the email-provider settings section (connect, validate, activate, encrypted-at-rest) needs zero new mental model for the AI-provider section (T21's `AISettings.tsx` is structurally identical to `EmailProvidersPage.tsx`). The detached-goroutine pattern is required, not optional, by `AGENTS.md` §4's public-status-page guarantee ("never calls Datadog live on a visitor request") extended to a second external dependency: an LLM call is slower and less reliable than a Datadog poll, so it must be even further removed from any request path that a visitor or the poll cycle depends on. 30s (not e.g. 10s/60s) was chosen with headroom above `internal/connectors/openai.Client`'s own ~20s HTTP timeout specifically so the outer context can't race the connector's own timeout classification (see `analyzer.go`'s doc comment on `analysisTimeout` for the full reasoning) - not an arbitrary round number.
- **Trade-off**: a genuinely slow/hung LLM call is silently discarded past `analysisTimeout` rather than retried or surfaced to an admin - a degraded service can go without its tooltip, or an auto-created incident without its description/closing-comment proposal, until the next transition regenerates one. ### AD-012 addendum: why `range` rejects while `page` clamps

- **Decision**: `AD-012`'s "invalid `?page=` clamps to `1`, never an error" convention is scoped specifically to pagination parameters and does not extend to `public-status-time-range-selector`'s `range` query parameter, which instead rejects an out-of-tier value with `422` (see `AD-020` above).
- **Reason**: `page` is an ordered scalar with an always-safe fallback (page 1 is always a reasonable thing to show instead of an invalid page number). `range` is an enum selecting between materially different, non-orderable views (24h vs. 90d are not "the same data, different offset" the way pages are) - silently substituting a different range than the one requested is more likely to mislead a caller into misreading the chart than clamping a page number ever is. `AD-012` itself remains correct and unchanged for pagination; this addendum exists only so a future reader of `AD-012` doesn't mistake `range`'s different validation behavior for an unexplained inconsistency.
- **Scope**: `internal/api/time_range.go`'s `parseRange`. Does not change `AD-012` or any existing paginated endpoint.

- **Status**: active
